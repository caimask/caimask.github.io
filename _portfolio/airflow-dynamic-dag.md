로그 수집 대상 약 300개를 MySQL에 row로 등록하기만 하면 Airflow DAG이 만들어지는 생성기를 직접 만들어 운영했습니다. 수집 대상이 늘면서 DAG을 만드는 과정 자체가 무거워졌고, 이를 자기 검토로 분석해 원인과 개선 순서를 정리했습니다.

역할: DAG 생성 코드 설계·개발, 자기 검토(2026-10)
{: .meta}

기술: Airflow 2.x · AWS Glue 4.0 · MySQL · Trino · OpenSearch · AWS SSM
{: .meta}

<div class="summary" markdown="1">

## 한눈에 보기 {#tldr}

- **만든 것**: 설정 row 하나가 DAG 하나가 되는 수집 파이프라인입니다. 대상을 추가할 때 코드 변경과 배포가 필요 없습니다.
- **문제**: 대상이 늘수록 DAG 반영이 느려지고, 스케줄 주기 안에 처리를 끝내지 못할 수 있는 상황이 생겼습니다.
- **판단**: 원인은 연산이 아니라 **파싱**이었습니다. 파싱 경로의 외부 호출이 "설정 수 × 파싱 주기 × 태스크 수"로 곱해졌습니다.
- **상태**: 개선 순서를 정했고, 아직 적용하지 않았습니다.

</div>

## 문제와 원인 {#problem}

Airflow는 DAG 파일을 정의가 아니라 **실행되는 코드**로 다룹니다. 스케줄러는 30초마다, 워커는 태스크 하나를 시작할 때마다 그 파일을 처음부터 다시 실행합니다. 파일 하나가 설정 row 300개로 DAG 300개를 만들고 있었으므로, 그 안의 비용이 모두 이 횟수만큼 반복됐습니다.

```
파싱 1회 = SSM 호출 1 + MySQL 조회 1 + (pool 조회·생성 + DAG 생성) × 300
워커:  태스크 1개를 돌리려고 DAG 300개를 다시 만듦
       → DAG 한 번 실행에 DAG 객체 약 2,100개, pool 조회·생성 약 2,100번
```

자기 검토에서 부하보다 더 급한 문제도 찾았습니다. MySQL 조회가 실패하면 파일 import가 실패하고, **수집 DAG 300개가 함께 UI에서 빠집니다.** 장애가 격리되지 않는 구조였습니다.

## 핵심 판단 {#decisions}

1. **급한 것은 장애 격리입니다.** 설정을 캐시에서 읽고, 조회가 실패하면 마지막 캐시로 버티게 합니다.
2. **파일을 나누기 전에 파싱 경로부터 비웁니다.** pool 조회·생성과 SSM 호출을 파싱 경로에서 빼고, 워커에서는 실행할 DAG 하나만 만듭니다(`get_parsing_context()`).
3. **파일 300개로 나누는 것은 그다음입니다.** 파일을 나누면 파싱이 병렬화되고 장애가 DAG 단위로 격리됩니다. 하지만 파일마다 드는 고정 비용이 남아 있으면 오히려 300배 나빠지므로, 순서를 바꾸면 안 된다고 판단했습니다.
4. **DAG 하나로 합치는 안(Dynamic Task Mapping)은 택하지 않았습니다.** 대상마다 재처리 단위와 선행·후행 흐름이 달라, DAG을 대상별로 나누는 지금 구조가 맞다고 봤습니다.
