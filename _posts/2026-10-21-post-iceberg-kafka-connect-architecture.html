Iceberg Sink Connector 구성도

Kafka 토픽의 레코드를 Iceberg 테이블에 쓰는 Kafka Connect Sink Connector가 실제로 어떤 컴포넌트로 나뉘어 돌아가는지, 소스 코드 기준으로 정리한 문서입니다.

Iceberg 1.5.2 패키지 io.tabular.iceberg.connect Connector 클래스 IcebergSinkConnector
참고. 이 저장소는 더 이상 유지보수되지 않습니다. 코드는 Apache Iceberg 본 프로젝트에 기증되었고, 현재 버전은 apache/iceberg/kafka-connect에 있습니다. 구조와 커밋 프로토콜은 거의 같으므로 이 문서의 내용은 upstream 버전을 이해하는 데에도 그대로 쓸 수 있습니다. 이 저장소에서도 이미 컨트롤 토픽 이벤트는 upstream 클래스(org.apache.iceberg.connect.events.*)를 사용합니다.

1. 한눈에 보기

핵심 아이디어는 파일 쓰기와 커밋을 분리하는 것입니다.

  • 모든 Task는 자기에게 할당된 파티션의 레코드를 읽어 Parquet/ORC/Avro 데이터 파일을 스토리지(S3, ADLS, GCS, HDFS 등)에 직접 씁니다. 하지만 Iceberg 커밋은 하지 않습니다.
  • Task 중 단 하나가 리더로 선출되어 내부에 Coordinator 스레드를 띄우고, 이 Coordinator만 Iceberg 카탈로그에 스냅샷을 커밋합니다.
  • Task와 Coordinator는 서로 직접 통신하지 않고 컨트롤 토픽(기본값 control-iceberg)이라는 별도 Kafka 토픽을 메시지 버스로 사용합니다.

이렇게 하는 이유는 docs/design.md에 정리되어 있습니다. Task마다 커밋하면 커밋 주기마다 Task 수 × 테이블 수만큼 스냅샷이 생겨 메타데이터가 비대해지고, 동시 커밋 충돌로 재시도가 늘어납니다. 커밋을 한 곳으로 모으면 커밋 주기(기본 5분)마다 테이블당 스냅샷 1개로 정리되고, Kafka 오프셋과 Iceberg 스냅샷을 묶어서 exactly-once를 보장할 수 있습니다.

2. 모듈 구성

Gradle 멀티 모듈 프로젝트이며, 배포 단위는 kafka-connect-runtime이 만드는 zip 하나입니다.

3. 런타임 구성도

소스 토픽 orders(파티션 4개)를 tasks.max=3으로 구동한 예시입니다. Kafka Connect가 파티션을 Task에 나눠 주고, orders-0을 받은 Task 0이 리더가 됩니다.

구성 요소 요약

IcebergSinkConnector

Connect 프레임워크가 띄우는 진입점. 하는 일은 tasks.max개의 Task 설정을 만들면서 Task마다 고유한 트랜잭션 ID 접미사(-txn-<UUID>-<i>)를 붙이는 것뿐입니다.

IcebergSinkTask

Connect의 SinkTask 구현. 파티션이 할당(open)될 때마다 TaskImpl을 새로 만들고, 회수(close)되면 버립니다. preCommit은 빈 맵을 반환해서 Connect가 오프셋을 커밋하지 못하게 막습니다.

Worker (Writer)

레코드를 테이블로 라우팅하고 테이블별 IcebergWriter로 파일을 씁니다. 커밋 요청이 오면 열린 파일을 닫고 결과(파일 목록 + 오프셋)를 넘깁니다.

CommitterImpl

각 Task의 컨트롤 토픽 창구. StartCommit을 받으면 Worker의 결과를 DataWritten/DataComplete로 보내고, 같은 Kafka 트랜잭션으로 소스 오프셋을 커밋합니다.

Coordinator

리더 Task 안의 별도 스레드. 커밋 주기를 재고, 응답을 모아 테이블별로 Iceberg 커밋을 실행합니다. 스냅샷 summary에 컨트롤 토픽 오프셋을 기록합니다.

Control Topic

Avro로 직렬화된 이벤트가 오가는 Kafka 토픽. 모든 이벤트에 groupId(= iceberg.control.group-id)가 들어 있어 여러 Connector가 같은 토픽을 공유해도 서로 섞이지 않습니다.

4. 클래스 계층

실제 객체 소유 관계를 위에서 아래로 그리면 다음과 같습니다. Task 하나에 Catalog, Worker, CommitterImpl이 한 세트로 붙어 있고, 리더 Task의 Committer만 CoordinatorThread를 추가로 가집니다.

IcebergSinkConnector // SinkConnector: taskConfigs()에서 transactional suffix 부여 └─ IcebergSinkTask × tasks.max // SinkTask: open/put/close/preCommit └─ TaskImpl // open() 때마다 새로 생성 ├─ Catalog // Utilities.loadCatalog() → CatalogUtil.buildIcebergCatalog ├─ Worker implements Writer // 레코드 라우팅 + 파일 쓰기 │ └─ IcebergWriterFactory // 테이블 load, 없으면 auto-create │ └─ IcebergWriter × 테이블 수 // RecordConverter + TaskWriter, schema evolution │ ├─ RecordConverter // Struct/Map → Iceberg Record │ └─ TaskWriter<Record> // Unpartitioned / PartitionedAppend / *DeltaWriter └─ CommitterImpl extends Channel // 컨트롤 토픽 producer(트랜잭션) + consumer └─ CoordinatorThread (리더만) // CoordinatorThreadFactoryImpl.isLeader() └─ Coordinator extends Channel // 별도 producer/consumer 보유 ├─ CommitState // commitId, 타이머, 응답 버퍼 ├─ Deduplicated // 같은 파일 경로 중복 제거 └─ ExecutorService // iceberg-committer 풀, 테이블별 병렬 커밋

Channel은 CommitterImpl과 Coordinator의 공통 부모로, 컨트롤 토픽용 Kafka 클라이언트 세 개(트랜잭션 Producer, read_committed Consumer, Admin)를 감싸고 send()와 consumeAvailable()을 제공합니다. 같은 Producer ID를 메시지 키로 써서 한 참여자가 보낸 이벤트의 순서가 유지되도록 합니다.

5. 데이터 쓰기 경로

Connect가 IcebergSinkTask.put(records)를 호출할 때마다 TaskImpl.put()이 다음 두 줄을 실행합니다. 이 두 줄이 Task 쪽 동작의 전부입니다.

writer.write(sinkRecords); // ① 레코드를 파일에 쓴다 committer.commit(writer); // ② 컨트롤 토픽을 폴링해 StartCommit이 왔으면 응답한다

① 레코드 → 파일

  1. 오프셋 기록. Worker.save()가 파티션별로 offset + 1과 타임스탬프를 기억합니다. 나중에 커밋할 "다음에 읽을 위치"입니다.
  2. 테이블 라우팅. 세 가지 방식이 있습니다.
    • 정적, 라우팅 필드 없음: iceberg.tables의 모든 테이블에 씁니다.
    • 정적, 라우팅 필드 있음: iceberg.tables.route-field 값이 테이블별 iceberg.table.<name>.route-regex와 맞는 테이블에만 씁니다.
    • 동적 (dynamic-enabled=true): 라우팅 필드 값을 소문자로 바꿔 그대로 테이블 이름으로 씁니다. 테이블이 없고 auto-create도 꺼져 있으면 조용히 버립니다.
  3. Writer 준비. 테이블마다 IcebergWriter를 한 번 만듭니다. 테이블이 없으면 첫 레코드의 스키마(또는 값에서 추론)로 생성합니다.
  4. 변환. RecordConverter가 Connect Struct나 Map을 테이블 스키마에 맞춰 Iceberg Record로 바꿉니다. 테이블 스키마가 기준이고, name mapping이 있으면 그것을 우선 씁니다.
  5. 스키마 진화. evolve-schema-enabled=true일 때 새 컬럼이나 타입 확장이 감지되면, 현재 파일을 닫고(flush) 테이블 스키마를 업데이트한 다음 새 Writer로 같은 레코드를 다시 변환합니다.
  6. CDC 연산. cdc-field가 지정되면 값의 첫 글자로 I/U/D를 판별해 RecordWrapper에 담아 씁니다. 값이 null인 레코드(tombstone)는 항상 무시합니다.

TaskWriter 선택 규칙

Utilities.createTableWriter()가 테이블 파티션 여부와 CDC/upsert 설정으로 Writer를 고릅니다. 파일 포맷과 목표 파일 크기는 테이블 속성에 iceberg.tables.write-props.*를 덮어써서 결정합니다.

일반 appendCDC 또는 upsert
파티션 없음UnpartitionedWriter (Iceberg 기본)UnpartitionedDeltaWriter
파티션 있음PartitionedAppendWriter (fanout)PartitionedDeltaWriter

Delta 계열(BaseDeltaTaskWriter)은 Iceberg의 BaseEqualityDeltaWriter를 씁니다. INSERT는 append, DELETE는 equality delete, UPDATE는 equality delete 뒤에 append입니다. upsert 모드는 CDC 필드가 없는 레코드를 모두 UPDATE로 취급합니다. 그래서 둘 다 Iceberg v2 테이블과 identifier 컬럼(id-columns 또는 테이블 스키마의 identifier field)이 필요합니다.

6. 커밋 프로토콜

커밋 한 번은 Coordinator가 만든 commitId(UUID) 하나로 묶입니다. 컨트롤 토픽에 오가는 이벤트는 다섯 종류입니다.

이벤트보내는 쪽내용구버전 이름 (1.4.x)
StartCommitCoordinator새 commitId. "지금까지 쓴 것 제출하라"CommitRequest
DataWritten각 Task테이블 1개분 data/delete 파일 메타데이터, 파티션 타입. 테이블 수만큼 여러 개CommitResponse
DataComplete각 Task할당된 모든 파티션의 오프셋·타임스탬프 목록. 데이터가 없던 파티션도 포함CommitReady
CommitToTableCoordinator테이블 1개 커밋 완료, 새 snapshot ID, vttsCommitTable
CommitCompleteCoordinator이번 commitId 전체 완료, vttsCommitComplete

Iceberg 1.5에서 Avro 직렬화가 바뀌었기 때문에 EventDecoder는 새 포맷으로 먼저 디코딩하고, 실패하면 kafka-connect-events 모듈의 구버전 스키마로 읽어 새 이벤트로 바꿉니다.

Coordinator의 판단 규칙

  • 완료 조건. CommitState.isCommitReady()는 현재 commitId에 대한 DataComplete들의 파티션 개수를 더해 리더 선출 시점에 계산한 전체 파티션 수와 비교합니다. Task 수가 아니라 파티션 수로 셉니다.
  • 타임아웃 = 부분 커밋. commit.timeout-ms 안에 다 모이지 않으면 받은 것만 커밋합니다. 이때 vtts는 기록하지 않습니다. 늦게 온 응답은 버퍼에 남아 다음 커밋에 포함됩니다.
  • vtts(valid-through timestamp)는 모든 파티션이 응답했고 모두 타임스탬프가 있을 때만, 그중 최솟값으로 정합니다. "이 시각 이전 데이터는 전부 반영됨"이라는 뜻이라 다운스트림에서 워터마크로 쓸 수 있습니다.
  • 커밋 방식. delete 파일이 없으면 트랜잭션 안에서 partition spec별로 AppendFiles를 실행하고, 있으면 RowDelta 한 번으로 data와 delete를 함께 커밋합니다. 테이블별 commit-branch를 지정하면 그 브랜치에 커밋합니다.
  • 실패 처리. 한 테이블이라도 실패하면 stopOnFailure로 멈추고 경고만 남깁니다. 응답 버퍼를 비우지 않으므로 다음 주기에 다시 시도합니다.

7. Exactly-once와 오프셋 관리

중복과 유실을 막는 장치는 두 구간으로 나뉩니다.

  1. 소스 토픽 → 컨트롤 토픽 구간. Task는 DataWritten/DataComplete 전송과 소스 오프셋 커밋을 하나의 Kafka 트랜잭션으로 처리합니다. 컨트롤 토픽 Consumer는 모두 read_committed이므로, Coordinator가 보는 파일 목록과 저장된 소스 오프셋은 항상 짝이 맞습니다.
  2. 컨트롤 토픽 → Iceberg 구간. Coordinator는 커밋할 때 스냅샷 summary에 그 시점의 컨트롤 토픽 오프셋을 함께 기록합니다. 다음 커밋 전에 테이블의 스냅샷 이력을 거슬러 올라가 이 값을 읽고, 그보다 앞선 오프셋의 이벤트는 건너뜁니다.

사용되는 Consumer Group

한 Connector가 Kafka에 consumer group을 네 종류 만듭니다. 오프셋을 리셋하려면 앞의 두 개를 모두 리셋해야 합니다.

그룹 ID (기본값)누가 쓰나무엇을 저장하나
cg-control-<connector>각 Task (트랜잭션으로 커밋)소스 토픽 오프셋의 원본(source of truth). Task 시작 시 여기서 requireStable로 읽어 Connect consumer 위치를 되감음 (context.offset())
connect-<connector>Kafka Connect 프레임워크소스 토픽 오프셋 사본. Sink 전용 그룹에 값이 없을 때만 의미가 있음. preCommit이 빈 맵이라 Connect 스스로는 커밋하지 않고, Task가 트랜잭션으로 대신 갱신
cg-control-<connector>-coordCoordinator컨트롤 토픽 오프셋(모든 테이블 커밋이 성공한 지점, low watermark)
cg-control-<UUID>각 Task의 Committer아무것도 커밋하지 않는 일회용 그룹. 컨트롤 토픽을 latest부터 읽기 위한 용도

Iceberg 스냅샷 summary에 남는 값

키값
kafka.connect.offsets.<control-topic>.<group-id>컨트롤 토픽 파티션별 오프셋 JSON. 예: {"0":1532}
kafka.connect.commit-id이번 커밋의 UUID
kafka.connect.vttsvalid-through timestamp (epoch ms). 부분 커밋이면 없음

이 값들은 Spark 등에서 SELECT summary FROM db.tbl.snapshots로 확인할 수 있어서, 커넥터가 어디까지 반영했는지 추적할 때 유용합니다.

재시작 시 복구

  • Task: cg-control-<name>의 오프셋으로 되감아서 읽습니다. 마지막 트랜잭션 이후에 썼지만 제출하지 못한 파일은 고아 파일로 남고(카탈로그에 등록되지 않음), 해당 레코드는 다시 읽어 새 파일로 씁니다.
  • Coordinator: …-coord 그룹의 오프셋부터 컨트롤 토픽을 읽어서 이전 리더가 처리하지 못한 DataWritten을 다시 모읍니다. 이미 일부 테이블에만 커밋된 경우는 테이블별 summary 오프셋 필터가 중복을 걸러냅니다.
  • 남은 위험: GC 등으로 세션 타임아웃보다 오래 멈춘 "좀비" Task가 나중에 트랜잭션을 완료하면 중복이 생길 수 있습니다. 설계 문서에 zombie fencing은 향후 과제로 남아 있습니다.

8. 리더 선출과 장애

CoordinatorThreadFactoryImpl.create()가 Task마다 Committer 생성 시점에 실행됩니다.

  1. Admin 클라이언트로 connect-<name> consumer group을 조회합니다.
  2. 그룹 상태가 STABLE일 때만 진행합니다. 리밸런스 중이면 아무도 리더가 되지 않고, 다음 리밸런스에서 다시 시도됩니다.
  3. 모든 멤버의 할당 파티션을 (토픽 이름, 파티션 번호) 순으로 정렬해 가장 앞의 것을 고릅니다. 그 파티션을 가진 Task가 리더입니다. 설계 문서는 "첫 번째 토픽의 파티션 0"이라고 표현하지만, 코드는 토픽 이름의 사전순으로 비교합니다.
  4. 리더는 그 시점의 전체 파티션 수를 totalPartitionCount로 고정하고 Coordinator 스레드를 시작합니다.
장애 시 동작. Coordinator 스레드에서 예외가 나면 스레드가 종료되고, 같은 Task의 다음 put()에서 IllegalStateException("Coordinator unexpectedly terminated")이 발생해 Task가 실패합니다. Connect가 리밸런스를 일으키면 모든 Task가 close → open을 거쳐 TaskImpl을 새로 만들고, 그 과정에서 리더가 다시 선출됩니다. 파티션 수가 바뀌어도 리밸런스가 일어나므로 totalPartitionCount가 다시 계산됩니다.

참고로 이 버전의 IcebergSinkTask는 flush()를 오버라이드하지 않습니다. 컨트롤 토픽 폴링은 put() 안에서만 일어나는데, Connect는 새 레코드가 없어도 주기적으로 빈 배치로 put()을 호출하므로 유휴 상태에서도 StartCommit에 응답할 수 있습니다.

10. 코드 읽는 순서

처음 읽는다면 아래 순서가 흐름을 따라가기 쉽습니다. 경로는 모두 kafka-connect/src/main/java/io/tabular/iceberg/connect/ 기준입니다.

  1. IcebergSinkTask.java와 channel/TaskImpl.java: 생명주기와 put()의 두 단계
  2. channel/Worker.java: 라우팅과 committable()
  3. data/IcebergWriter.java, data/Utilities.java: 변환, 스키마 진화, Writer 선택
  4. channel/Channel.java: 트랜잭션 전송과 폴링
  5. channel/CommitterImpl.java: 시작 시 오프셋 되감기, StartCommit 응답
  6. channel/CoordinatorThreadFactoryImpl.java: 리더 선출
  7. channel/Coordinator.java, channel/CommitState.java: 커밋 주기, 완료 판정, Iceberg 커밋
